## 1. Executive summary

The underlying engineering is careful in the places that matter most for correctness: the affordance-gating framework (`src/affordance.py`) is real and does raise on violation where it's actually wired in, the statistical machinery that exists (Wilson intervals, grouped permutation tests) is implemented correctly, and every number this audit independently recomputed — the two Fisher p-values, the pooled-residual cosine tables, the H3a Mann-Whitney statistic — checked out exactly against the underlying data. No fabricated numbers were found. That said, the submission's persuasive framing currently outruns what's actually enforced or committed in several places that matter for a "detecting covert loyalties" hackathon whose whole pitch is auditability. The three most consequential gaps: (1) the README's marquee claim that affordance hygiene is "enforced at runtime, not asserted in prose" is false for the project's two strongest behavioural results (R7/R9) and for Result 3 — `capture.py`, `quantify.py`, and `elicit.py` never import `affordance.py` at all, so the "level 1-2" labels on the headline findings are prose, exactly the practice the project says it avoids; (2) the pivotal Fisher's-exact p-values (p=0.0006, p=0.32) that decide "Presence: Yes/high confidence" vs. "suggestive" for the two organisms are never computed by any committed script and live only as repeated prose across four documents, with one document (`ORGANISM_C_IS_BASE_2026-07-24.md`) even swapping which organism has which p-value; (3) `docs/BIBLIOGRAPHY.md` cites a fabricated paper (wrong author, wrong content, mismatched URL) as the "single closest precedent" for the project's headline method — an unflagged, invented reference backing the project's strongest claim. Beyond these, the newer cross-model SAE feature-naming work (`SAE_CROSSMODEL_SPREAD`) is mergeable-but-wrong as currently worded: it ranks 131,072 features by raw spread with no significance testing or multiple-comparisons correction, conflates a global reconstruction-fidelity check with per-feature significance, calls a base-anchored replay "model-neutral," and never engages the project's own bibliography entry warning that a generic pretrained SAE is a weak instrument for exactly this kind of narrow-edit feature-naming — yet it names five features as "priority targets" for follow-up without a wrong-principal control, despite the same note independently reproducing R1's finding that organisms A and B are nearly indistinguishable at this level of granularity. There is also a real, if not yet triggered, correctness bug in `sae_diff.py`'s replay (BPE re-tokenization can silently misalign the generated-token span) — verified empirically not to have corrupted any of the 128 real trajectories currently committed, but unguarded. None of this is data fabrication (with the single exception of the bibliography citation); it is a consistent pattern of claims running ahead of what's actually enforced, computed, or committed — precisely the gap the project's own rules were written to catch, and precisely the kind of thing worth fixing before the numbers get cited in the final submission.

**H2 — BPE re-tokenization can silently misalign the replayed generation span**
- **Location:** `src/sae_diff.py:104-118` (`cmd_encode`)
- **Issue:** Replay concatenates `prompt_text + generated_text` and re-tokenizes from scratch, then slices the "generated span" using `n_prompt_tokens`, a count computed by a *separate* tokenizer call in `capture.py` at generation time. BPE is not associative under concatenation (`tokenize(a)+tokenize(b) != tokenize(a+b)`), and neither `capture.py` nor `sae_diff.py` persists real generation-time token ids or checks that the retokenized prefix matches the prompt-only tokenization. This directly contradicts the file's own docstring invariant ("identical tokens in identical positions → position-aligned feature activations → the diff is clean").
- **Evidence:** Reproduced with the real Qwen2.5 tokenizer: a prompt ending in the chat-template's `...assistant\n` concatenated with a completion starting `\n\n...` shifts the token at the exact index `sae_diff.py` uses as the span start from token 198 to a different merged token (1406). The existing null-test (`PILOT_MECHANICS_VERIFIED`, "null_max_abs_delta = 0.0") does not catch this — it replays the same (mis-tokenized) string twice, which is deterministic regardless of fidelity to the true generation. Independently checked all 128 real committed completion records (`results/capture_7b_darkstar/`, `results/pilot_0p5b/`) with the real tokenizer: zero currently trigger the bug (none start with a boundary-spanning whitespace/newline sequence), so no committed number is presently corrupted — but nothing guards against it recurring. *(Verification downgraded this from the reporter's original "critical" to "high" on exactly this point: real, unguarded defect; zero current impact, verified empirically.)*
- **Recommendation:** Persist actual `input_ids` in `capture.py`'s completion records so replay can feed token ids directly; or, at minimum, assert the retokenized prefix equals a prompt-only tokenization and fail loudly if not.
- **Dimension:** code-core

**H3 — `capture.py`'s default dtype is the one flagged elsewhere in this repo as unsafe on the target hardware**
- **Location:** `src/capture.py:352` (`--dtype` default), `:64-77` (`load_organism`)
- **Issue:** `capture.py --dtype` defaults to `float16`. The sibling script `sae_diff.py` defaults to `float32` for the same model family on the same hardware, with the explicit comment "fp32 default: Qwen2.5 is bf16-trained and NaNs in fp16 on pre-Ampere" — a risk also documented in `AGENTS.md` and `docs/PROVENANCE_DARKSTAR_2026-07-24.md` as a known M40/sm_52 footgun. No NaN/Inf check exists anywhere in `capture.py` before writing `acts_*.npz`, and `json.dump`'s default `allow_nan=True` would silently serialize NaN into derived JSON.
- **Evidence:** `capture.py:352` vs. `sae_diff.py:317-318` — opposite defaults, same repo, same model, same explicit rationale in the neighbor file. The three real committed captures happened to use fp32 only because the operator manually overrode the flag (per `PROVENANCE_DARKSTAR_2026-07-24.md`), not because the code enforces it.
- **Recommendation:** Change `capture.py`'s default to `float32` to match `sae_diff.py`, or add an explicit NaN/Inf check on pooled activations before writing `.npz` and abort/warn loudly.
- **Dimension:** code-core

**H4 — Grouped-CV leakage guard silently disables itself in exactly the low-scenario-diversity regime it exists to protect**
- **Location:** `src/probes_loyalty.py:178-187` (`grouped_auroc`); same fallback pattern in `src/kaggle_demo.py:183-186`
- **Issue:** When the number of distinct scenario groups is smaller than `n_splits` (default 5), `grouped_auroc` falls back to fully ungrouped `StratifiedKFold` rather than shrinking `n_splits` to fit the available groups. This is exactly the near-duplicate-trajectory leak the module's own docstring says the project "has been burned by... before." `run_affordance_cell` computes the H1 supported/refuted verdict directly from the resulting AUROC, with no check of the `grouped_cv` flag.
- **Evidence:** Reproduced live: 3 groups of 20 near-duplicate rows, perfectly separable by group, `n_splits=5` → `{'auroc': 1.0, 'grouped_cv': False}`, identical to the fully ungrouped call. `run_affordance_cell` (lines 372-384) reads only `auroc['auroc']`, never `grouped_cv`. Confirmed no existing test (`test_demo_logic.py`) exercises the low-group-count regime.
- **Recommendation:** When ≥2 groups exist, keep `StratifiedGroupKFold` and shrink `n_splits = min(n_splits, n_unique_groups)`; fall back to ungrouped only with exactly one group. Have `run_affordance_cell` refuse/flag an H1 "supported" verdict when `grouped_cv` is False on real (non-synthetic) data.
